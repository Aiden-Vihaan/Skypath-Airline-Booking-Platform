# SkyPath — Reflection

## Project Reflection

SkyPath was developed as an exploration of how UX methods can be applied to a complex, multi-stage digital service.

The project initially appeared to be primarily an interface-design problem.

However, the process demonstrated that many of the most important design challenges existed before visual design began.

Information architecture, decision-making, content hierarchy, and interaction logic had a greater influence on the quality of the experience than visual styling alone.

---

## What I Learned

### 1. Complex Interfaces Require Structural Thinking

Airline booking contains many connected decisions.

A change to one part of the journey can affect several other parts.

For example, baggage selection can influence:

- total price;
- passenger requirements;
- booking review;
- payment;
- post-booking management.

This reinforced the importance of designing relationships between features rather than designing each screen independently.

---

### 2. Information Architecture Is a UX Tool

The information architecture work demonstrated that navigation is not simply a menu-design exercise.

The structure determines how users understand the product.

Developing the content inventory, card sorting, navigation model, and sitemap helped identify where information should live and how different tasks should connect.

---

### 3. Personas Are Decision-Making Tools

The personas became more useful when treated as constraints rather than fictional profiles.

A family traveller, student traveller, senior traveller, and business traveller can encounter the same interface but have fundamentally different priorities.

This encouraged the design to ask:

> "Does this decision work for different contexts?"

rather than:

> "Does this screen look good?"

---

### 4. Transparency Is Part of Interaction Design

Price transparency was initially considered a visual requirement.

During the design process, it became clear that transparency is fundamentally an interaction problem.

Users need to understand:

- what they selected;
- what it costs;
- what is included;
- what changes when they modify a selection.

This led to dynamic price updates and stronger review-stage communication.

---

### 5. Accessibility Should Be Designed Early

Accessibility cannot be effectively added only after the interface has been completed.

It affects:

- information hierarchy;
- navigation;
- interaction targets;
- content;
- forms;
- error handling;
- assistance workflows.

This project therefore reinforced the value of incorporating accessibility considerations from the beginning of the design process.

---

## What I Would Improve

### 1. Broader User Research

A future iteration should involve a larger and more diverse participant group.

Testing should include:

- frequent travellers;
- first-time flyers;
- families;
- students;
- older adults;
- users with different accessibility requirements.

This would help distinguish design assumptions from consistently observed behaviour.

---

### 2. Quantitative Validation

Future testing could include measurable metrics such as:

- task completion rate;
- time on task;
- error rate;
- abandonment rate;
- confidence rating;
- perceived cognitive load.

This would make it possible to compare alternative designs more rigorously.

---

### 3. Real-World Validation

The prototype should eventually be evaluated with realistic airline data.

For example:

- real fare rules;
- real baggage restrictions;
- actual seat maps;
- realistic cancellation policies;
- live airport information.

This would expose constraints that are difficult to model accurately in a conceptual prototype.

---

### 4. More Extensive Accessibility Testing

The next iteration should include evaluation with assistive technologies and users with different accessibility requirements.

Potential areas include:

- keyboard navigation;
- screen-reader behaviour;
- focus management;
- contrast;
- form errors;
- accessible seat selection;
- assistance requests.

---

### 5. Service-Level Exploration

The next stage could expand beyond the interface itself.

Airline booking is part of a larger service ecosystem involving:

- airports;
- airlines;
- payment providers;
- customer support;
- baggage systems;
- check-in;
- notifications.

A future version could therefore include a service blueprint to understand relationships between front-stage and back-stage systems.

---

## Design Maturity

The project progressed from a broad problem space to a structured UX system.

The maturity of the work can be understood as:

**Problem → Research → Structure → Interaction → Interface → Prototype → Evaluation**

This progression was important because it prevented the final interface from being developed without a supporting rationale.

---

## Limitations

SkyPath remains a conceptual UX project.

The main limitations are:

- limited research participants;
- prototype rather than production environment;
- simulated airline data;
- limited real-world operational constraints;
- no long-term behavioural analytics.

The project therefore represents a design hypothesis supported by structured UX exploration and prototype evaluation.

---

## Future Direction

A future version of SkyPath could explore:

- personalised travel recommendations;
- intelligent fare comparison;
- disruption-aware rebooking;
- multimodal accessibility support;
- contextual travel assistance;
- predictive baggage recommendations;
- personalised loyalty experiences;
- stronger post-booking service integration.

These features should only be introduced where they demonstrate measurable user value.

---

## Final Reflection

The most important learning from the project was that good UX is not primarily about producing attractive screens.

It is about understanding a problem, structuring complexity, identifying user needs, making decisions explicit, testing assumptions, and iterating on evidence.

SkyPath helped me move from thinking about UX as interface creation toward thinking about UX as a **systematic design and problem-solving discipline**.

That shift is the most significant outcome of the project.
